## 一句话结论

**核心记账逻辑是对的，测试也都能跑通。** 主要问题有三类：

1. **真实数据的安全**：数据放在程序文件夹里、没有自动备份、启动锁可能卡住打不开。
2. **以后好不好改**：代码被写成“压缩”的一长行，数据结构还是“试用版”，改起来容易出错。
3. **文档太乱**：大量历史流水账和术语，新手和接手者都很难找到“现在到底是什么规则”。（这一条本次已经处理。）

## 问题清单（按严重程度排序）

每一条都写了：现在是什么样、为什么是问题、建议怎么做。**本次 PR 只改文档，没有改任何程序代码**，下面的代码问题都是建议，等你确认后再分批做。

### 🔴 高：影响真实数据安全，或可能让软件打不开

#### 1. 数据放在程序文件夹里，升级要靠手动复制

- **现在**：Windows 版把账本存在解压出来的程序目录下的 `trial-data/` 里，备份在旁边的 `backups/`。升级新版本时，要按说明把旧目录里的 `trial-data` 和 `backups` 整个**手动复制**到新目录（还必须包括里面所有 `restored-*` 文件夹和指针文件）。
- **为什么是问题**：只要删掉旧程序文件夹、把新版解压覆盖到旧目录、或者少复制一个文件夹，就可能丢数据或打开的是旧账本。原始需求第 10.2 节明确要求“数据目录与安装目录分离，升级不清空用户数据”，现在的做法和需求不一致。
- **建议**：把数据固定放到用户自己的文件夹（例如“文档\钱来数据”）。新版第一次启动时，自动找到旧位置的数据，先做一份完整备份，再搬过去。这样以后升级只要解压新版、双击就行。

#### 2. 没有自动备份

- **现在**：只能在“备份”页手动点“导出完整备份”。需求第 10.2 节要求“运行期间按日自动备份，并保留轮换”。
- **为什么是问题**：忘记手动备份时，一旦电脑硬盘出问题或误操作，就没有可恢复的副本。
- **建议**：每天第一次打开软件时自动做一份完整备份，只保留最近若干份（例如 30 份），并在界面上显示“上次备份时间”。

#### 3. 启动锁太复杂，异常退出后可能一直打不开

- **现在**：为了防止两个程序同时写同一个账本，代码自己实现了一套“写入锁”。异常退出后要解锁，需要调用 Windows PowerShell 去查询“这台电脑的编号”和“原来那个进程的启动时间”。10 月 15 日已经真实出现过“账本正在使用或有残留锁”，10 月 16 日改进过一次，但仍然依赖 PowerShell 查询。
- **为什么是问题**：公司电脑经常限制 PowerShell，或者查询失败；这时锁会永远无法自动解除，软件每次都提示“账本正在使用或有残留锁”。而使用说明又要求用户“不要删除 `.writer-lock`”，用户自己没有办法解决。
- **建议**：这是单人单机软件。Electron 自带的“只允许开一个窗口”加上 SQLite 自带的文件锁已经能防止重复写入。建议去掉 PowerShell 依赖；万一锁真的卡住，在界面上提供“确认没有其他窗口在用，继续打开”的按钮，而不是让用户束手无策。

#### 4. 最新代码还没有在目标 Windows 10 电脑上实际验收

- **现在**：10 月 13 日的“Windows 验收通过”是你当时做的决定，那一轮的修改并没有在 Windows 真机上测试。10 月 16 日的构建只在 GitHub 提供的 Windows Server 上自动测过，而且下载包 7 天后已过期删除。**目前仓库里没有一个可以直接下载使用的 Windows 包。**另外，原来专门用于打包的分支 `codex/windows10-offline-acceptance` 已经不存在了，下次打包要在 GitHub 上手动触发（见 [开发指南](DEVELOPMENT.md#windows-离线包)）。
- **建议**：下次出新包后，按 [Windows 验证清单](WINDOWS_VALIDATION.md) 在那台 Windows 10 上实际走一遍，尤其是断网首次启动、OCR、强制关闭后重开、升级旧数据。

### 🟠 中：现在不会出事，但会让以后改代码容易出错

#### 5. 代码写成“压缩”格式，几乎没法读

- **现在**：很多代码挤在一行里，最长的一行有 3000 多个字符。界面主文件 `prototype/src/main.tsx` 一个文件 42KB，里面有 30 多个状态变量和几乎所有页面逻辑。仓库没有代码格式化工具（如 Prettier）和代码检查工具（如 ESLint）。
- **为什么是问题**：人很难看懂，改一处容易误伤另一处，代码审查（看 PR 改了什么）也几乎看不出来。
- **建议**：先加自动格式化，一次性把代码排版整齐（**只改排版，不改任何功能**，用现有测试保证不变）；之后在做新功能时，逐步把 `main.tsx` 拆成“总览、费用、报销、预支、备份”几个页面文件。

#### 6. 账本数据结构还是“试用版”

- **现在**：整个账本（全部费用、预支、报销、修改历史）存成数据库里**一行很长的 JSON 文本**，每保存一次就整段重写。没有“数据格式版本号”，也没有“数据升级（迁移）”机制。同一套业务规则在“保存代码”（`trial-ledger.cjs`）和“备份校验代码”（`ledger-backup.cjs`）里各写了一遍。而且软件每次启动都会用这套非常严格的校验检查账本，任何一处不符合，软件就拒绝打开。
- **为什么是问题**：以个人用量（每年几百上千笔）来说，速度和容量都够用，不急。但以后加字段、改规则时，没有规范的升级步骤，旧数据可能被读错；两处规则改了一处忘了另一处，旧备份可能恢复不了，甚至软件打不开。
- **建议**：短期先加“数据格式版本号 + 按版本升级”的小框架，并让两处规则共用同一份代码。长期是否换成正规的表结构，需要一次谨慎的数据迁移，必须单独评估、先用合成数据演练，不急着做。

#### 7. 文件夹和名字有误导性

- **现在**：`spike/`（意思是“技术试验”）里其实是正式的后端代码，`prototype/`（原型）里是正式界面。软件包名叫 `xx-finance-stage0`，Windows 安装程序的描述还写着 “Stage 0 dependency probe; not a production ledger”（阶段 0 依赖探针，不是正式账本）。数据目录叫 `trial-data`、`stage0-trial`。
- **为什么是问题**：新接手的人（包括 AI）会以为这些是临时代码，而不知道它们就是正式产品。
- **建议**：代码文件夹可以安全地改名（例如 `app/main`、`app/ui`）。**数据目录的名字先不要动**，它们涉及已有的真实数据，改名要配合第 1 条的数据迁移一起做。

#### 8. 最核心的一份账本测试不在仓库里

- **现在**：`tests/trial-ledger.test.cjs` 和 `tests/test_receipt_fields.py` 两份测试，因为当时担心里面的金额来自真实截图，被排除在 git 外，只留在原来的电脑上。其他测试覆盖了大部分功能，但“新增费用、报销超额被拒、保存中途失败全部回滚”这类最基础的测试在仓库里不完整。
- **建议**：用明确虚构的数据重写这两份测试并提交到仓库。

#### 9. 提交代码时没有自动测试

- **现在**：仓库唯一的 GitHub 自动任务是“打 Windows 包”，只能手动触发。普通提交和 PR 不会自动运行测试。
- **建议**：加一个只跑 `npm run build` 和 `npm test` 的 Linux 自动检查，每次 PR 自动运行。大约几分钟，在 GitHub 免费额度内。

#### 10. 保存带截图的费用，依赖 OCR 程序能启动

- **现在**：保存截图前，代码会先调用 OCR 辅助程序检查“图片是否完好”（这一步不做识别）。如果 OCR 程序启动不了（例如被公司杀毒软件拦截），**连截图都存不了**，只能放弃附件。
- **建议**：图片完好性检查改在主程序里做，OCR 程序只负责识别。这样 OCR 出问题时，至少还能手动填写并保存截图。

#### 11. 恢复备份会不断产生新的账本文件夹，备份文件夹看不出日期

- **现在**：每次恢复都会新建一个 `restored-一串随机编号` 的文件夹，旧的永远保留，靠一个“指针文件”指向当前正在用的那个。备份文件夹叫 `backup-一串随机编号`，看不出是哪天备份的。
- **为什么是问题**：时间久了占空间；用户很难判断哪个文件夹才是真正在用的数据、哪个备份是最新的；手动升级时还必须把这些文件夹全部复制过去。
- **建议**：备份文件夹名带日期时间；提供“清理旧恢复目录”的入口（清理前提示并先备份）。和第 1 条一起做。

#### 12. Electron 版本有已知安全公告

- **现在**：使用 Electron 44.7.0，`npm audit` 报告有高风险安全公告（证书相关），44 系列后续补丁版本已修复。另有几个构建工具的中等风险提示。
- **为什么影响不大**：软件完全离线、不加载外部网页，实际风险低。
- **建议**：下次打包前顺手升级到 Electron 44 系列的最新补丁版本，并重新跑一遍测试。

## 建议的下一步顺序

1. **先搭安全网**（只动工具，不改功能）：加 PR 自动测试（第 9 条）、补回核心测试（第 8 条）、一次性格式化代码（第 5 条）。这一步让后面每次修改都更放心，风险最低。
2. **再保护真实数据**：自动备份（第 2 条）、数据目录和程序分离 + 自动搬迁（第 1、11 条）、简化启动锁（第 3 条）。
3. **出一个新的 Windows 包，在 Windows 10 真机验收**（第 4、12 条）。
4. 之后再按你的优先级做新功能（上一节的清单）。

如果你**已经在 Windows 上用真实数据记账**，建议把第 2 步（尤其是自动备份）提到最前面。
