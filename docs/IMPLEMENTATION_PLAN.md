## 1. 确认需求与默认假设
单人、单账本、人民币，在 Mac 开发、Windows x64 使用。公司实际拨款全部记预支；报销仅登记进度，不另行收付款。首版接待、办公、预支及退还、负余额、多对多报销、发票、离线 OCR、完整备份恢复、CSV 和批次材料包。
不做账号、云服务、多级审批、复杂财务模块、银行同步、多币种、验真。
- 零余额起账；首版不做历史期初导入，不提供任意余额调整。
- Windows 11 x64 为候选基线；具体版本及硬件要在 Windows 验证开始前固定。Mac 不替代 Windows。
- 只记录实际付款；待付款、未确认 OCR 留草稿。报销草稿首版不持久化。
- 真实商户退款暂未支持，不能伪装成纠错；若用户日常必需，交付前单独补齐。
- CSV 和材料包必做；XLSX、专用打印排版延后。
- 本机用户目录与系统权限保护数据；首版不另做账本密码或密钥管理。

## 2. 需补齐的规则及最小改动
|问题|影响|采用规则|
|---|---|---|
|编辑批次使用当前待报销额|自身旧分配占用额度|可用额 = 费用金额 - 其他有效批次分配；整批事务修改|
|仅明确发票侧上限|一笔费用可能关联超额票面|费用侧、发票侧累计分配均不超对应原额|
|同票不同扫描件|哈希不同导致额度重复|文件哈希去重与票据业务标识去重独立；一个发票实体、多份附件|
|票据身份不完整|无法可靠排重|先归档，核对身份后才金额分配；不宣称自动排除全部重复|
|缺票定义不清|部分票额误当齐全|无发票/票额不足/已覆盖；前两类均属缺票，不代表合规判断|
|后续改票影响旧材料|同批次重导内容不同|导出保存批次修订、分配、文件哈希清单；历史导出不覆盖|
|事实表与资金表双存金额|重复扣款或不一致|资金流水采用只读视图，来源仅为有效真实收支|
|退款允许延后|余额可能失真|未实现时显著标注，不用改原额替代；有日常需求则交付前实施|

## 3. 模型与计算
以下为目标正式模型，尚未全部实现。阶段 0 实际保存为 `trial_state` 单行 JSON（费用、报销批次及分配、预支金额数组及可选的新增记录元数据）、附件元数据表和请求操作表；已有最小预支到账新增/查看，没有预支纠错/退还、发票分配、版本迁移或完整前后值审计。独立 SQLite 探针的关系表、外键、资金视图与快照不等于试用业务层已经采用这些结构。

- expense：稳定编号、类别、实际付款金额分、日期、商户/采购摘要、备注、有效/作废、修订。
- expense_item：费用外键、名称、条目金额分；数量和单价选填。优惠为明确减项，运费为加项，总费用为正。
- advance / advance_return：实际到账/退还金额分、日期、备注、状态；不强制逐笔绑定。
- reimbursement：编号、日期、总额、有效/撤销、备注、报账单号、修订、请求标识。
- reimbursement_allocation：批次、费用、分配金额分；同批次同费用唯一。
- invoice：类型、核对后业务标识、票面额、日期、购销方、元数据核对状态。
- invoice_allocation：发票、费用、金额分；同组合唯一。
- attachment 及有真实外键的关联：哈希、相对路径、原名、类型、大小；原件不覆盖。
- import_draft：文件与 OCR 候选，不计正式统计。
- operation_log：对象、动作、前后值、时间、请求标识。
- export_manifest：批次修订、分配、材料哈希。

关系：费用 ← 报销分配 → 批次；费用 ← 发票分配 → 发票。两条链独立；重复报销不重复消耗票额。

余额 = Σ有效预支 − Σ有效费用 − Σ有效退还预支
本人垫付 = max(0, -余额)
已报销 = Σ有效批次对该费用分配；待报销 = 费用原额 − 已报销。
票剩余额度 = 票面可分配额 − Σ该票的费用分配。

所有金额整数分，输入字符串严格解析；禁止静默舍入，转换和汇总校验安全整数。
业务日期 YYYY-MM-DD，操作时间另存。全账本余额不受列表筛选影响。
报销总额等于正数分配合计；零行不保存；报销不受预支或余额限制。
降低费用或发票原额先校验分配；冲突拒绝，不裁剪历史。作废费用先解除有效关联，留痕不硬删除。
写事务内复核额度和修订号；请求标识唯一，重复返回原结果、同标识异内容拒绝。
批次、分配、操作历史同事务；撤销保留历史。报销测试比较资金完整内容与余额。

## 4. 交互方案
### 费用列表
浅灰底、白色工作区、克制强调色、系统中文字体、金额右对齐，列表优先。
接待/办公共用组件与两个入口，日期/关键词/状态/缺票筛选。列：勾选、日期、商户/摘要、支出、已报销、待报销、状态、发票。
选中显示待报销合计；登记面板可添加其他类别费用。全账本余额与筛选合计分开。

2026-10-12 已授权的阶段 0 总览调整：总览列表仅展示与点击详情，去掉多选及底部登记工具条；顶部登记报销可在无预选时打开，费用选择统一在报销面板内完成。接待／办公类别页仍保留上述选择入口。标题显示“你好，小徐同学”及设备本地年月日星期，截图 OCR 留在费用录入内。
点行打开右侧详情，查看明细、附件、票额分配及报销历史。
### 录入面板
接待：金额/默认今天/商户；办公：摘要/金额/默认今天；明细、备注可展开。
保存或保存并继续；负余额允许，展示保存后垫付。
识别录入的目标为原图+候选字段；金额、付款日期、类别核对，缺失留空，不把票面日期当付款日期。阶段 0 已实现的单图费用录入、确认保存及附件边界见 [OCR_REVIEW_UI](OCR_REVIEW_UI.md)；不再使用独立不入账面板作为当前入口。
复用上一笔、保存并继续及物品明细属于后续计划，尚未实现；复用时不得复制交易号、票额或报销分配。
### 报销面板
日期默认今天、默认分配所选全部剩余；按费用日期+稳定编号排序。
列：费用、原额、其他有效登记、本次可分配、本次分配、保存后待报销。
改总额重新建议；改行同步合计。编辑时排除自身旧分配。超过选中合计拒绝，不触及未选中费用。阶段 0 已有新增及撤销整批；修改批次入口与持久化命令尚未实现，不能将模型中排除旧分配的测试当作修改功能验收。
保存提示仅登记、不收付款；撤销确认只恢复待报销。资金负数不阻止。

## 5. 技术路线与依赖门槛
Electron + React + TypeScript + SQLite，Forge 构建。主进程最小受限 IPC，渲染 sandbox/contextIsolation，禁 Node 直接访问。
SQLite 优先验证 better-sqlite3；不引 ORM。OCR 候选 RapidOCR + ONNX Runtime CPU，Python 独立进程，stdio 通信，不启 HTTP 服务，不改账本。
Python 用项目隔离环境，不改系统 Python。Windows 用 PyInstaller 目录模式，预置模型、字典、DLL、运行时；全部明确本地路径。
PDF 候选 PDF.js：文本优先、不足页渲染 OCR；OFD 仅归档。
Windows x64 机器构建安装器，Mac 包不换后缀冒充 Windows。构建环境可联网，用户首次使用不得下载模型。

验证矩阵：
1. 开发和生产 Electron 启动、受限 IPC、本地资源加载。
2. Electron ABI 匹配的 SQLite 加载、写读、重启、事务回滚、外键与一致性快照。
3. 真正本地 OCR 文字与位置输出；本地模型缺失显式失败，超时/取消/崩溃不伤账本。
4. Windows 干净用户、无 Node/Python、断网安装并首次识别；中文/空格路径、输入法、Ctrl+V、100/125/150/200% 缩放。
5. 记录系统/CPU/内存/包哈希、冷启动/首次与连续识别时间、内存，不编造性能目标或通过状态。
6. 单独核查代码、模型、字典许可证及可分发性。签名、系统提示、公司电脑策略均实际记录。
7. 至少 30 份脱敏 OCR 样本覆盖干扰金额、优惠、待付款/退款、模糊图、中文、发票、混合 PDF；文字识别、字段提取、确认入账分开验收。

备份用 SQLite 一致性快照+附件+清单+版本+哈希；不复制正在写入的单个数据库文件。
文件先暂存校验后移动、再提交引用；清理无引用残件，不能保留成功却缺附件的记录。恢复先暂存校验，保留旧账本可回退。
以上是目标可靠性要求；试用保存只在普通失败时清理本次附件，异常退出的无引用残件尚不自动清理。完整备份、恢复与迁移的拟定步骤及未执行验收见 [备份恢复方案](BACKUP_RECOVERY_PLAN.md)。
