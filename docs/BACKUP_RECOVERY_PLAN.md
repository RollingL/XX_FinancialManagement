## 1. 现状和保护对象

| 数据来源 | 正常入口及数据根目录 | 保护范围 |
| --- | --- | --- |
| 浏览器开发试用 | Vite；项目 `.local-data/` | `trial.sqlite`、SQLite 运行时旁文件、`attachments/` |
| Electron 试用 | 开发与打包程序按各自 `app.getPath('userData')/stage0-trial/` 解析 | 同上；实际路径须由对应运行环境确认，不猜测或用浏览器目录代替 |
| 显式隔离测试 | 主进程／开发服务的 `XX_FINANCE_DATA_DIR` | 只允许指定的新建合成测试目录，不回退到正常入口目录 |

浏览器和 Electron 两套数据不自动同步，不合并成一个账本备份。每次备份明确选择一个来源、一个根目录并标注来源类型；同一机器上开发与打包程序若解析为不同目录，也须分别识别和保护。备份到另一入口属于跨目录恢复，须明确选择目标，不隐式合并。

现有试用库是 `trial_state` 单行 JSON、`attachments` 元数据和 `operations` 请求表；没有正式结构版本、账本身份或全量修订历史。备份必须保存其已有全部内容，不在备份过程中转换成规划中的正式模型，不伪造缺失的历史。关系型业务表与资金视图目前只在独立探针中，不能据此声称产品已有备份能力。

Git、费用 CSV、报销材料包均不能替代完整备份。备份目的地须是用户明确选择的本地位置，避开源码、安装目录及应用数据根目录；不默认放入云同步目录，不自动上传。异盘／外部介质可用于应对整盘损坏，使用前同样需明确位置。不得在本轮检查这些位置或搬运真实材料。

## 2. 拟定备份格式

首个实现采用一个自包含目录，先创建唯一 `.partial` 暂存目录，成功后发布为唯一完成目录；不覆盖上一次备份。压缩归档可后续评估，不作为最小交付的前提。

```text
backup-<backup_id>/
  manifest.json
  database.sqlite
  attachments/<受管相对文件名>
  COMPLETE
```

`manifest.json` 拟包含：

- 备份格式版本、备份 ID、完成时间（UTC）、应用版本及已提交源码版本（如有），来源类型 `browser-trial`／`electron-trial`／`isolated-test`。
- 账本结构标识与结构指纹；当前试用格式可标记为 `trial-state-json-v0`，这是拟定的导出标识，不表示现有数据库已有该版本字段。识别不到已支持结构则停止，不能猜测版本。
- 数据库相对路径、字节数和 SHA-256；所有受管附件的相对路径、大小、SHA-256 及是否被快照引用。操作记录及分配完整保存在数据库中。
- 核对摘要：费用／有效及撤销批次数、分配数、操作数、附件数，支出、预支、余额、本人垫付、已报销和待报销合计。金额以整数分的十进制字符串记录，避免 JSON 数字累计越界；摘要只用于校验，数据库仍是事实源。
- 校验结果与清单格式版本。完整清单包含私有账目信息，只留在备份内；公开或 Git 内的证据仅记录合成数据结果，不记录真实金额、商户、绝对个人路径或截图。

`COMPLETE` 拟保存清单 SHA-256 和备份 ID，在所有写入与校验成功后才生成。哈希用于发现损坏，不是加密或来源认证；本方案不新增账本密码、账号或密钥管理。没有完成标记、清单哈希不符或未知版本的目录不得提供恢复。

## 3. WAL 一致性与备份步骤（待实现）

SQLite WAL 可能包含尚未写回主数据库的已提交内容，不能只复制运行中的 `.sqlite` 主文件，也不能在持续写入时依次复制主文件与旁文件并宣称获得一致快照。依据：[SQLite WAL 文件规则](https://www.sqlite.org/wal.html)。

拟使用 SQLite Online Backup API（现有驱动的 `db.backup()` 路线已在合成探针试用）生成独立数据库快照，数据库快照之外仍要协调附件的一致性。依据：[SQLite Online Backup API](https://www.sqlite.org/backup.html)。以下应用级控制尚未实现：

1. 显示并核对所选来源，检查目标不是源目录／子目录、不是已有完成备份；检查可用空间和权限。空间不足时停止，不能先删除旧备份腾空间。
2. 取得所选账本的跨进程维护锁，停止接受新写入并等候正在保存的费用、分配和附件操作结束。单个窗口的 `busy` 标记不够；无法确认所有写入者遵守锁时要求关闭相关实例并停止备份，不能静默继续。
3. 在维护锁覆盖下，用 SQLite API 将逻辑一致快照写入 `.partial/database.sqlite`。不要手工清空 WAL、删除旁文件或把 checkpoint 当作数据库与附件的联合快照。
4. 从新快照读取附件元数据，盘点受管附件目录并复制原始字节。有效引用必须有文件且大小与哈希吻合；缺失或损坏即失败。无引用的普通受管文件也保留到备份并在清单标记，不自动关联、删除或变成费用。拒绝符号链接、目录外路径及未识别文件布局，不顺着链接读取其他个人文件。
5. 对副本核对数据库、业务关系、附件及金额摘要，关闭备份连接；验证它能在没有源 WAL／SHM 文件的干净目录独立重开。所需的单文件规范化只能发生在备份副本，不修改源数据。维护锁保持到数据库和附件均完成校验。
6. 写清单与完成标记，对文件及目录持久化完成做平台验证，再将暂存目录发布为完成目录。完成前的异常只能留下明确未完成材料，不能提示“备份成功”。最后释放维护锁。
7. 记录完成时间、备份 ID 和检查结果。失败时保留源库、源附件及旧完成备份；只清理本次确定归属的临时产物，未确认归属的残件保持原位并提示人工检查。

所有副本与完成目录的具体创建操作均需后续授权；本文没有可直接对真实目录执行的复制命令。

## 4. 恢复前校验与业务核对（待实现）

恢复默认先到新建的隔离目录演练，不覆盖现用账本。恢复入口不能调用会自动建库的 `createLedger()` 来探测未知目录，避免在缺失或失败状态下生成空账本掩盖问题。

- 核对来源类型、目标目录、备份版本和结构；未知／更高版本拒绝。清单路径必须是根目录内的规范相对路径，拒绝绝对路径、`..`、重复名称、符号链接及大小写冲突；Windows 中文／空格路径单独测试。
- 按清单验证文件全集、大小与 SHA-256，再以不会自动建库的只读方式检查数据库。预期结构必须匹配；`integrity_check` 返回正常后，还要独立检查外键（如果该格式存在）和业务关系。数据库结构检查不替代业务校验，依据：[SQLite integrity_check](https://www.sqlite.org/pragma.html#pragma_integrity_check)。
- 当前 JSON 格式须完整解析并验证安全整数分、类别、合法日期、ID 唯一性、每条分配对应费用、同批次同费用唯一、正数分配、有效累计分配不超费用原额、批次合计等于分配之和。附件引用必须可解析且与文件一致，已撤销批次及请求记录须保留。
- 比较恢复前备份快照与恢复后完整费用／预支／批次／分配／操作内容，派生资金流水逐项比较并比较余额；不能只看条数或首页总额。报销状态仍由有效分配派生。恢复不新增预支、费用或报销，不重算 OCR 来改写数据。
- 未实现的预支明细、发票关系或历史不得在恢复时臆造。将来支持正式模型后，再增加真实预支、退还、发票双向额度及修订历史的验收，不能用当前试用演练替代。
- 摘要、文件或业务校验任一失败，停止并保留现用账本，不提供“忽略错误强制恢复”。未被引用的受管文件继续标记为未引用，不自动挂到费用。

## 5. 覆盖恢复、迁移和失败回退（待实现）

真实覆盖恢复须先展示来源、目标、备份时间和核对摘要，并取得对应操作授权。随后先为目标现用账本完成一份按上述流程验证过的全量备份；失败就停止覆盖。恢复暂存目录、回退目录及切换步骤应在同一文件系统内，跨盘输入先复制到本地暂存并校验。

拟定切换协议：

1. 持有跨进程维护锁，关闭目标全部 SQLite 连接和附件文件句柄，暂停正常账本启动；先检查是否有上次未完成恢复。
2. 将已验证的新数据放入目标旁的唯一暂存目录，持久化恢复日志，记录 `prepared`、原目录、暂存目录和回退目录的标识。
3. 原目录改名到回退目录，记录 `old-preserved`；新目录改名到目标，记录 `new-installed`。两次改名不是一个原子事务，必须分别记录并验证断电／崩溃时的恢复路径。
4. 在仍禁止业务写入时完成重开、附件及金额一致性检查，成功后记录 `verified` 并恢复入口。原目录和覆盖前备份继续保留，不在同一操作中删除。
5. 任一步骤失败就停止业务启动，恢复原目录为活动目录；若回退也受占用或权限阻挡，保持两份目录与日志不动并报告，不能自动创建空库。下一次启动先处理恢复日志，不让普通建库路径抢先运行。

迁移是单独的版本转换，不能隐含在备份或恢复中。先验证源全量备份，再在副本上转换并核对完整事实与附件；通过后才采用上述切换流程。失败继续使用旧版本和原账本，不原地破坏性升级。当前没有迁移框架，本方案不开展 JSON 试用结构到正式关系表的转换。

Windows 的目录改名、文件占用、权限、落盘与启动恢复必须实测；不能用 Mac 的改名成功宣称 Windows 崩溃安全。
